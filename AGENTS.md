# Agent / LLM handoff — Learning Narrative Kit

Use this file when an LLM (or human) authors a new unit **without** a specialized bot. Schema wins if anything conflicts: `schema/README.md`.

## What this kit is

Story-first pedagogy: a cohesive term set woven into **one** meaningful narrative so the words gain shared context. Hover glossaries and review decks are secondary lookup/retrieval — not the point.

Inspired by: 8th-grade “use the vocab in a paragraph,” Goldratt’s *The Goal*, NADF.

## Repo layout

```
examples/<unit_id>/     # SOURCE — write here
  unit.yaml
  glossary.yaml
  narrative.md
  review.yaml           # optional but expected for exam tracks
docs/<unit_id>/         # GENERATED — never hand-edit; from render_unit.py
docs/index.html         # landing cards — GENERATED by tools/build_hub_index.py; edit the builder, not the page
docs/unit.css, unit.js  # shared Pages assets
schema/                 # authoring contract + informal schema
tools/                  # validate_unit.py, render_unit.py, render_track.py
tracks/<track>.yaml     # reading order for a track → contents page + prev/next links
briefs/<brief_id>.brief.yaml   # the author's instructions for one job (schema/BRIEF.md)
workshop/<brief_id>/    # plan, status, reviews, CANDIDATE chapters; never published
research/               # background notes (schema wins on conflict)
```

Marks in prose: `[[term_id|surface text]]`

Scene artifacts (ticket / console / gui / table) are optional fenced blocks in `narrative.md`. Schema: `schema/README.md` → Scene artifacts. HTML is still generated only by `render_unit.py`.

## Setup (once)

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

`.venv` at the repo root is the only supported location — it is gitignored, so a fresh clone has none until you run the above. If your system `python3` already has PyYAML, you can skip the venv and run the tools with `python3` directly; that is the only dependency.

## Authoring workflow (brief → plan → draft → review → preview)

Use this when a job starts from material rather than from a finished chapter. The author
decides; the agent drafts; `tools/author.py` keeps the books. Format and decision points:
`schema/BRIEF.md`. Every command below runs from the repo root.

**The four starting points.** Each one begins with a brief in `briefs/`. The examples are
in the repo and run as written:

| You have | `mode` | Example brief |
|---|---|---|
| A set of related terms (bare or defined) → one story | `term-set` | `briefs/example-term-set.brief.yaml` |
| A whole course glossary → a connected multi-chapter narrative | `course-glossary` | `briefs/tamarack-mis-companion.brief.yaml` |
| Lessons, slides or notes → a narrative | `source-material` | `briefs/example-source-material.brief.yaml` |
| New material → another chapter in an established track | `track-extension` | `briefs/example-track-extension.brief.yaml` |

```bash
# 1. Check the brief: required fields, defaults applied, definitions that block drafting
.venv/bin/python tools/author.py brief-check briefs/example-term-set.brief.yaml
.venv/bin/python tools/author.py brief-check briefs/example-source-material.brief.yaml
.venv/bin/python tools/author.py brief-check briefs/example-track-extension.brief.yaml
.venv/bin/python tools/author.py brief-check briefs/tamarack-mis-companion.brief.yaml

# 2. Start the resumable record (any mode)
.venv/bin/python tools/author.py status briefs/<id>.brief.yaml --init

# 3. course-glossary only: plan the companion, then check coverage and the drafting gate
.venv/bin/python tools/author.py plan briefs/tamarack-mis-companion.brief.yaml            # writes workshop/<id>/plan.yaml + plan.md
.venv/bin/python tools/author.py plan briefs/tamarack-mis-companion.brief.yaml --refresh  # after inputs change; keeps the author's parts
.venv/bin/python tools/author.py plan-check briefs/tamarack-mis-companion.brief.yaml --chapter ch10

# 4. Draft the candidate in workshop/<id>/candidates/<unit_id>/ (same files as examples/<unit_id>/),
#    then review it. --chapter checks it against the plan; omit both flags for a unit with no brief.
.venv/bin/python tools/author.py review workshop/<id>/candidates/<unit_id> \
    --brief briefs/<id>.brief.yaml --chapter chNN --out workshop/<id>/reviews/chNN-r1.md

# 5. Validate and preview, outside docs/ (the preview folder is gitignored)
.venv/bin/python tools/validate_unit.py workshop/<id>/candidates/<unit_id>
.venv/bin/python tools/render_unit.py workshop/<id>/candidates/<unit_id> --out workshop/<id>/preview

# 6. Where does the job stand?
.venv/bin/python tools/author.py status briefs/<id>.brief.yaml
```

Rules the workflow enforces, or asks you to keep:

- **Definitions before claims.** A bare term or an agent-`proposed` definition blocks
  drafting until it has a source or the author confirms it. When only terms are supplied,
  ask the author what each ambiguous one means (record it as `sense`) before writing.
- **Approval gates.** `plan-check --chapter` refuses a chapter until the author sets
  `approved: true` in `plan.yaml` and the chapter's situation (goal, complication,
  decision, cost, carries_forward) is filled in.
- **Bounded revision.** `max_revisions` in `status.yaml` (default 2). At the cap, the chapter
  goes back to the author with the open questions; it does not get a third pass.
- **Candidates are not published.** Nothing in `workshop/` reaches Pages. Promoting a
  candidate means copying its files into `examples/<unit_id>/` with the author's
  go-ahead, then the ship checklist below.
- **Three kinds of evidence, kept apart.** The review report separates automated checks
  (pass/fail), heuristic flags (a person looks), and editorial judgment (the author
  decides). It does not claim the chapter teaches better; that needs readers.

`workshop/tamarack-mis-companion/` is the worked example: a 264-term plan for the ten MIS
modules, and a candidate rewrite of MIS 10 with its reviews r0 (the accepted version, as
a baseline) through r3.

## Add a new unit (ship checklist)

1. **Collect the term set** that belongs together (one exam/lesson cluster).
2. **Choose one forcing situation** where those ideas must interact (ticket plot, plant floor, etc.). Build each beat as goal / complication / pivot, with the marked terms on the complication or the pivot (`schema/README.md` → Beat structure).
3. **Create** `examples/<unit_id>/` by copying the nearest sibling unit’s file shapes.
4. **Write** `narrative.md` (story-first) and `glossary.yaml` (every id used ≥1 in the narrative).
5. **Write** `unit.yaml` (`unit_id` must match folder name and Pages path) and `review.yaml` (cards from glossary; include `tier`).
6. **QA by hand** — cover test, density, tiers, tooltip contract (`schema/README.md`).
7. **Validate (must PASS):**
   ```bash
   .venv/bin/python tools/validate_unit.py examples/<unit_id>
   ```
8. **Render (do not hand-edit HTML):**
   ```bash
   .venv/bin/python tools/render_unit.py examples/<unit_id>
   ```
9. **Landing card** — add a card under the right track in `HTML_CONTENT` in `tools/build_hub_index.py`, then run `python3 tools/build_hub_index.py` to rewrite `docs/index.html` (render_unit.py does **not** update the landing page). `python3 tools/check_hub_links.py` must PASS (CI runs it).
10. **Track (if the unit belongs to one)** — add it to `tracks/<track>.yaml` in reading order, then:
    ```bash
    .venv/bin/python tools/render_track.py tracks/<track>.yaml
    ```
    This writes the contents page `docs/<track_id>/index.html`. Re-render the unit and its old and new neighbours so their Previous / Next links update.
    If the track has `glossary: true`, also run `tools/render_glossary.py tracks/<track>.yaml` so the A-Z glossary picks up the new terms.
11. **Commit** `examples/<unit_id>/`, `docs/<unit_id>/`, `docs/index.html`, and any track files. Push `main`. Pages serves `/docs`.

Expected URL: `https://cwarloe.github.io/learning-narrative-kit/<unit_id>/`

## Before a pull request

Run all of these. Each one caught something real on the Tamarack track.

1. `validate_unit.py` on every unit you touched: PASS, and no unexplained WARN. Units
   with `heading_rule: scene` also get the heading check.
2. Re-render (`render_unit.py`, and `render_track.py` if a track changed). Only commit
   `docs/` changes for the units you meant to change; an older unit whose output shifts
   on re-render is pre-existing drift, so leave it out.
3. If the unit has a builder (for example `examples/*/workbook/build_workbook.py`), run
   it and confirm every check is `ok`. Don't commit regenerated binaries whose only
   change is a timestamp.
4. Recompute any number you added or changed in the prose, and check dates and
   standing facts against the track's timeline.
5. Open the rendered page in a headless browser at desktop and phone widths: marks
   render, no horizontal scroll, no console errors, new artifacts look right.
6. After the PR is up, read the review bot's comments, reply on each thread before
   pushing the fix, and re-audit the whole unit if the fix moves structure.
7. If you change Episode 7, Drill 1 (its capture table or its passwords), regenerate
   `portland-desk/artifacts/jared-telnet-capture.pcap` with
   `tools/generate_ep07_telnet_capture.py` (needs `pip install scapy`), copy it and the
   workbench into `docs/portland-desk/`, and run `python3 tools/check_ep07_capture.py`.
   CI runs the same check and fails if the table, the answer key, the capture, or the
   mirror disagree.

## Validate rules (mechanical)

| Check | Severity |
|-------|----------|
| Glossary + narrative load | fail |
| Every glossary id marked ≥1 | fail |
| No mark ids missing from glossary | fail |
| Mark density | report |
| Missing `tier` when any tier present | warn |
| `Priya` or `Harrowmere` in narrative | fail |
| Heading rule (units with `heading_rule: scene`): heading at chapter start, heading or break with nothing under it, heading over fewer than ~270 words, more than one heading per ~500 words | warn |

## Authoring contract (summary)

Full text: `schema/README.md`. Non-negotiables:

- Narrative is the learning object; glossary coheres inside it.
- The story supports the course (textbook, lectures, study tools); it doesn't carry it. Its job is connectedness.
- Cover test: strip `[[...]]`; story still teaches the central relationships.
- Technical explanation is fine when the scene earns it, preferably as a back-and-forth; metrics point, they don't decide (`schema/README.md` rules 8–9).
- Tooltip = `definition` + optional `context` only; `refs` stay sidebar.
- Two tiers when used: `exam` = study targets; `support` = readability jargon; flavor unmarked.
- HTML is generated only via `tools/render_unit.py`.

## Copy-paste prompt for a new chapter

Paste into any capable LLM with this repo checked out:

```
You are authoring a learning-narrative unit for this kit.

Read and follow:
- AGENTS.md (this playbook)
- schema/README.md (authoring contract)
- For Portland Desk Sec+: examples/PORTLAND_DESK.md
- Clone file shapes from the nearest examples/<sibling>/

Task: create examples/<UNIT_ID>/ with unit.yaml, glossary.yaml, narrative.md, review.yaml
for topic: <TOPIC / exam cluster>.

Then run validate_unit.py (must PASS), render_unit.py, add a card in tools/build_hub_index.py and re-run it,
and commit examples/<UNIT_ID>/ + docs/<UNIT_ID>/ + docs/index.html.

Constraints from the track docs apply. Do not hand-edit generated HTML.
Do not invent port numbers or exam definitions that contradict the course source.
```

## Done definition

A unit is done when: validate PASS, render succeeded, landing card present, cover test passes, sticky teaching beats can be named in one sentence each, and `docs/` is pushed for Pages.

## Core Standards & Production Knowledge Base

When authoring narrative stories, hands-on workbenches, terminal simulations, or art briefs, all agents must adhere to the foundational research standards in `docs/research/`:

1. **Plain-English & Vocabulary Standard (`docs/research/PLAIN_ENGLISH_STYLE_GUIDE.md`):**
   - Strictly prohibits L&D, educational psychology, and software architect jargon ("invariants", "falsifiable hypothesis", "rubric", "pedagogical", "heuristic" in general prose, "scaffolding").
   - Enforces U.S. high-school graduate readability and in-context technical vocabulary introduction.
2. **Visual Art Direction & Technical Panels (`docs/research/VISUAL_ART_DIRECTION.md`):**
   - Governs the "Clear Technical Cutaway" (Ligne Claire) art style and Pacific Northwest atmosphere.
   - Enforces the **Zero-Text Rule** on all AI image generation to eliminate hallucinated lettering.
   - Mandates Image-to-Image (Img2Img) workflow with real reference photos for hardware precision.
   - Contains the master aspect ratio directory (`16:9`, `21:9`, `4:3`, `1:1`, `3:4`) and full episode prompt catalogue.
3. **Pedagogical Agency Architecture (`docs/research/PEDAGOGICAL_AGENCY_ARCHITECTURE.md`):**
   - Resolves the "Already Solved" dilemma (Dramatic vs. Pedagogical Fallacy).
   - Enforces the **Dynamic Fading Apprenticeship** across the 13 episodes (Symmetrical Tickets $\rightarrow$ Interleaved Cliffhanger Handoffs $\rightarrow$ Co-Pilot Dispatcher $\rightarrow$ Incident Commander).
4. **Interactive Components Specification (`docs/research/INTERACTIVE_COMPONENTS_SPEC.md`):**
   - Syntax and client-side behavior for ````lnk-terminal` (zero-backend in-browser CLI simulation) and ````callout-panel` (responsive graphic novel schematics).
5. **Track Canon & Author Bibles:**
   - `docs/research/PORTLAND_AUTHOR_BIBLE.md`: Character arcs, 3-act story snowflake, episode causal beat matrix.
   - `docs/research/PORTLAND_CURRICULUM_PLAN.md`: Whole-task 4C/ID competency progression across CompTIA A+, Network+, and Security+.
